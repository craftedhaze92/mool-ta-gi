# KIS 시세 어댑터

한국투자증권 OpenAPI(KIS)를 감싸는 **서버 전용** 모듈이다. `app/api/quotes` 라우트 핸들러만
이걸 호출하고, 브라우저는 항상 우리 BFF(`/api/quotes`)만 본다. API 키가 클라이언트로
새어나가지 않게 하려는 구조다.

`index.ts`를 포함한 모든 파일이 `import 'server-only'`로 시작한다. 클라이언트 컴포넌트에서
실수로 import하면 `next build`가 실패한다. 예외는 `mapper.ts` 하나 — 순수 변환 함수라
자격증명을 건드리지 않고, 그래야 Vitest에서 단독 테스트가 된다.

## 구성

| 파일            | 역할                                      |
| --------------- | ----------------------------------------- |
| `token.ts`      | 접근토큰 발급·캐싱                        |
| `rate-limit.ts` | KIS 호출 간격 제어 (전역)                 |
| `quotes.ts`     | 시세 조회, 청크 분할, 종목 단위 실패 격리 |
| `mapper.ts`     | KIS 문자열 응답 → `Quote` 정규화 (순수)   |
| `raw-types.ts`  | KIS 원문 스키마 (zod)                     |
| `errors.ts`     | `KisError` + 사용자 응답으로의 정규화     |

응답 계약(`Quote`, `parseCodesParam` 등)은 이 디렉터리가 아니라 `../quote-contract.ts`에 있다.
`app` 레이어는 FSD 규칙상 `entities`를 import할 수 없어서 계약이 `shared`에 있어야 하고,
동시에 클라이언트도 읽어야 하므로 server-only 영역 밖이다.

## 토큰 캐시의 한계 (알고 쓸 것)

KIS 토큰은 **24시간 유효**하고, **발급 후 6시간 이내 재요청에는 같은 토큰이 그대로 온다.**
그리고 실제로 새 토큰이 발급될 때마다 **계좌주에게 카카오톡 알림이 간다.**

`token.ts`는 모듈 스코프에 토큰과 만료 시각을 들고, 만료 1시간 전에 갱신하며, 동시 요청이
몰려도 발급이 중복되지 않게 in-flight promise를 공유한다.

**하지만 이 캐시는 인스턴스 로컬이다.** Vercel serverless는 트래픽에 따라 인스턴스를 여러 개
띄우고, 각 인스턴스가 자기 토큰을 따로 발급한다. 콜드 스타트마다 발급 요청이 한 번씩 나간다.

지금 이걸 감수하는 근거:

- 위의 '6시간 이내 재요청 = 같은 토큰' 규칙 덕에 인스턴스가 몇 개든 KIS 쪽에서는 대부분
  기존 토큰을 되돌려준다. 실질 발급은 하루 1~2회이고 알림도 그만큼만 간다.
- BFF 응답에 `s-maxage`를 걸어 CDN이 흡수하는 만큼 인스턴스 기동 자체가 줄어든다.

**근본 해결 (이전 후보): Upstash Redis / Vercel KV.**
`kis:token` 키에 토큰과 만료 시각을 두고 `SET NX`로 발급 락을 잡으면 인스턴스가 몇 개든
발급은 한 번이다. `getAccessToken()`의 시그니처를 바꾸지 않고 `token.ts` 내부만 교체하면
되도록 설계해 두었다.

## 만료 시각만 믿으면 안 된다 (실측으로 확인)

**토큰을 새로 발급하면 앞서 발급된 토큰이 무효화된다.** 다른 프로세스 — 로컬 디버깅
스크립트, 다른 배포 인스턴스, 같은 앱키를 쓰는 다른 앱 — 가 한 번만 발급해도 우리 캐시에
든 토큰이 조용히 죽는다. 만료 시각은 아직 한참 남아 있는데도 그렇다.

그때 KIS는 이렇게 응답한다:

```
HTTP 500
{"rt_cd":"1","msg1":"유효하지 않은 token 입니다.","msg_cd":"EGW00121"}
```

여기서 두 가지가 중요하다.

1. **HTTP 상태 코드만 보고 판단하면 안 된다.** KIS는 500을 주면서 진짜 원인을 본문에
   담는다. 상태 코드로 먼저 갈라내면 유량 초과(`EGW00201`)와 토큰 만료(`EGW00121`)를
   구분할 수 없고, 회복 가능한 실패가 종목별 '시세 없음'으로 묻힌다.
   그래서 `quotes.ts`는 상태 코드와 무관하게 본문을 먼저 파싱한다.
2. **토큰 거절은 종목 단위 실패가 아니다.** 모든 종목이 똑같이 겪는다. `runBatches`는 이걸
   위로 올리고, `fetchQuotes`가 `invalidateToken()` 후 딱 한 번 전체를 재시도한다.
   이 회복 경로가 없으면 프로세스가 재시작될 때까지 모든 조회가 실패한다.

부수 효과로, 개발 중에 토큰을 발급하는 임시 스크립트를 돌리면 실행 중인 dev 서버의 토큰이
죽는다. 디버깅은 되도록 BFF(`/api/quotes`)를 통해서 하자.

## 만료 계산에 `expires_in`만 쓰는 이유

토큰 응답에는 `access_token_token_expired`(`"YYYY-MM-DD HH:mm:ss"`)도 온다. 하지만 타임존
표기가 없는 KST naive 문자열이라, UTC로 도는 서버에서 그대로 파싱하면 9시간 어긋난다.
`expires_in`은 상대 초라 시계 오차와 타임존에 면역이므로 이쪽만 쓴다.

## 전일 종가 (`prevClose`)

`inter2_sdpr`, 즉 "주식 **기준가**"를 쓴다. 평상시에는 전일 종가와 같지만
권리락·액면분할·신규상장일에는 갈라진다.

그래도 기준가를 쓰는 이유: KIS가 주는 `inter2_prdy_vrss`(전일 대비)와 `prdy_ctrt`(전일
대비율) 자체가 기준가 대비로 계산된 값이다. 등락을 다루는 화면에서는 기준가가 정합적이다.
값이 없거나 0이면 `현재가 − 등락`으로 역산한다.

진짜 전일 종가가 필요해지면 같은 응답의 **`inter2_prdy_clpr`** 로 바꾸면 된다.
`mapper.ts` 한 줄이다.

## 유량 제한 — 문서와 실측이 다르다

공식 샘플(`kis_auth.py`)은 실전 계정에서 호출 간 0.05초를 쉰다. 초당 20건이라는 뜻이다.
**이 계정에서 실측한 값은 초당 약 1건이었다.**

| 호출 간격  | 목표 속도 | 결과                              |
| ---------- | --------- | --------------------------------- |
| 1000ms     | 1 req/s   | 30회 중 30회 성공                 |
| 500ms      | 2 req/s   | 10회 중 7회 성공 (3회 `EGW00201`) |
| 300ms 이하 | 3+ req/s  | 실패율 비슷하게 유지 (30~40%)     |

포털에 걸린 "[중요] 신규 고객 초당 호출 제한 안내"(2026.03.20) 공지가 원인으로 보인다.
공지 본문은 JS 렌더링이라 읽지 못했다. **계정마다 다를 수 있으니 이 수치를 절대값으로
믿지 말 것.**

이 실측이 API 선택을 뒤집었다. 초당 1건이면 단건 조회로는 10종목에 10초가 넘게 걸려
쓸 수 없다. 그래서 **배치 API를 쓴다.**

## 왜 배치 API(`intstock-multprice`)인가

`GET /uapi/domestic-stock/v1/quotations/intstock-multprice`, tr_id `FHKST11300006`.
한 번에 **30종목**. 요청은 `FID_COND_MRKT_DIV_CODE_1..30` / `FID_INPUT_ISCD_1..30` 번호쌍.

실측으로 확인한 동작:

- 30종목 요청 → `rt_cd 0`, 행 30개. **31개를 넣으면 조용히 30개까지만 처리한다** →
  청크 분할은 우리 몫이다 (`MULTI_PRICE_CHUNK_SIZE`).
- **행은 요청 순서로 온다.** 조회 실패 종목도 행 자체는 돌아오는데 값이 전부 빈 문자열이고
  `inter_shrn_iscd`까지 비어 있다. `['005930','999999','000660']` → `[005930, (빈 행), 000660]`.
  그래서 **응답의 종목코드가 아니라 인덱스로 요청 종목과 맞춘다.** 종목 단위 실패 격리는
  이 방식으로 유지된다 — 빈 행 하나가 나머지 29종목을 망치지 않는다.

필드 이름이 단건 API와 완전히 다르다: `inter2_prpr`(현재가), `inter2_prdy_vrss`(전일 대비),
`inter2_sdpr`(기준가), `inter2_prdy_clpr`(**진짜 전일 종가**), `inter_kor_isnm`(종목명).

유량 제한 에러는 종목 단위로 삼키지 않고 위로 올려 429로 내보낸다 — 다른 종목도 똑같이
겪을 문제라 부분 실패로 위장하면 안 된다.

## 간격 제어는 전역이다 (`rate-limit.ts`)

KIS로 나가는 모든 요청은 `paced()` 게이트를 지난다. 모듈 스코프 큐가 호출 **시작** 간격을
1.2초로 벌린다.

호출부마다 sleep을 넣는 방식으로는 부족하다. BFF는 요청마다 핸들러가 따로 도는데,
브라우저가 `/api/quotes`와 `/api/indices`를 동시에 부르거나 **사용자가 둘이기만 해도**
서로의 간격을 모른 채 동시에 KIS를 친다. 실제로 스모크 테스트에서 연속 호출 중 하나가
429로 떨어졌다.

큐에는 task가 아니라 **게이트만** 이어 붙인다. 한 호출이 실패했다고 뒤따르는 호출이
영원히 막히면 안 되기 때문이다 (`rate-limit.test.ts`가 이걸 지킨다).

**토큰 발급은 이 게이트를 타지 않는다.** 별도 한도(분당 1회)를 쓰고 24시간 캐시되어 거의
나가지 않으며, `paced()` 안에서 다시 `paced()`를 부르는 중첩을 피하기 위해서다.

한계는 토큰 캐시와 같다 — 이 큐도 **인스턴스 로컬**이라 서버리스 인스턴스가 여러 개 뜨면
각자 자기 큐를 가진다. 지금은 응답의 `s-maxage`가 CDN에서 흡수해 주는 것에 기대고 있고,
근본 해결은 토큰과 함께 공유 저장소로 옮기는 것이다.

**일별 호출 제한은 공식 문서에서 확인하지 못했다.**

## 토큰 발급도 분당 1회다

`POST /oauth2/tokenP`를 짧은 간격으로 두 번 부르면 두 번째가 거절된다(실측). 커뮤니티에
널리 알려진 "1분에 1회" 제한이 실재한다는 뜻이다. 캐싱이 선택이 아니라 필수인 이유다.

## 아직 하지 않은 것

- **KOSPI/KOSDAQ 지수** — `market-header` 위젯은 여전히 목데이터를 쓴다.
  지수는 별도 엔드포인트(`inquire-index-price`)라 다음 작업으로 남겼다.
- **공휴일 휴장 판정** — `shared/lib/market-hours.ts`는 평일 09:00~15:30만 본다.
- **유량 제한 초과 시 재시도** — 지금은 곧바로 429로 내보내고 사용자의 '다시 시도'에
  맡긴다. 백오프 재시도를 넣으면 한도를 더 악화시킬 수 있어 보류했다.
